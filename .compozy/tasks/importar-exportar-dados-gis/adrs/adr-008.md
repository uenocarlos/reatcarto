# ADR-008: Batch Import API Endpoint

## Status

Accepted

## Date

2026-08-10

## Context

Importing up to 5,000 elements via sequential calls to the existing `elements/create.php` endpoint would incur unacceptable latency online (5,000 round-trips) and produce an oversized outbox offline. The PRD requires merge and replace strategies with transactional semantics and server-side PostGIS validation (`geojson_validate_for_element`, `ST_IsValid`).

## Decision

Add a dedicated batch import endpoint `POST /php/elements/import.php` that accepts a map id, strategy (`merge` | `replace`), a client mutation id for idempotency, and an array of element payloads. The server executes replace (delete all elements with photo cascade, then insert) or merge (insert only) inside a database transaction, enforcing `ELEMENTS_PER_MAP` and per-element validation.

Offline import enqueues a single `map/import` outbox mutation containing the same payload; `SyncEngine` delivers it to the batch endpoint on flush.

## Alternatives Considered

### Alternative 1: Sequential client calls to existing CRUD endpoints

- **Description**: Loop `create.php` / `delete.php` from the browser.
- **Pros**: No new server code.
- **Cons**: 5,000 HTTP requests; no atomic replace; slow offline outbox.
- **Why rejected**: User chose batch endpoint.

### Alternative 2: Chunked batch (100 elements per request)

- **Description**: Multiple batch calls with partial commits.
- **Pros**: Lower per-request memory.
- **Cons**: Replace is not atomic across chunks; complex rollback.
- **Why rejected**: User chose single batch endpoint; chunking deferred to server streaming if needed later.

## Consequences

### Positive

- Atomic replace import on the server.
- Single network round-trip for online imports.
- One outbox entry for offline bulk import.

### Negative

- Large request bodies (up to 5,000 elements) require memory and timeout tuning.
- New SyncEngine handler for `map/import` mutation type.

### Risks

- PHP memory/timeout on very large imports; mitigated by 5,000-element cap and server-side streaming insert within transaction.

## Implementation Notes

- Reuse `photos_delete_for_element()` during replace (same as individual delete).
- Return summary: `{ imported, skipped, errors[] }`.
- Idempotency via `client_mutation_id` table (existing sync pattern).
