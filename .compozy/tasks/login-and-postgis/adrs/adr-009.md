# ADR-009: Filesystem Photo Storage with Controlled URLs

## Status

Accepted

## Date

2026-07-31

## Context

Field users attach photos to elements; published maps expose those photos to anonymous visitors. The UI calls an unimplemented upload helper. Photos must support preview, size/count limits, failed-upload isolation, and cascade deletion with elements/maps/accounts.

## Decision

Store photo binaries on the PHP server filesystem under a configured uploads root. Persist metadata in a `photos` table (owner via element/map, content type, size, storage path, `version`, `client_mutation_id`). Serve bytes only through PHP routes that re-check private ownership or current public/moderation state. Reject unsupported types and oversize files before creating a valid attachment row. Partial uploads never become publicly fetchable.

## Alternatives Considered

### Alternative 1: S3-compatible object storage with signed URLs

- **Description**: External bucket for media.
- **Pros**: Scalability and CDN friendliness.
- **Cons**: Extra credentials, SDK, and ops for current single-server deployment.
- **Why rejected**: Unnecessary for this version's scale and ops model.

### Alternative 2: BYTEA / base64 in PostgreSQL

- **Description**: Store image bytes in the database.
- **Pros**: Single backup domain.
- **Cons**: Bloats DB, complicates streaming and size limits.
- **Why rejected**: Filesystem + metadata table is simpler for large binaries.

## Consequences

### Positive

- Straightforward cascade: delete DB row and unlink file.
- Authorization stays centralized in PHP.
- Works offline by caching blobs in the IndexedDB/account cache separately.

### Negative

- Backup must include filesystem and database.
- Multi-server deploy would need shared storage later.

### Risks

- Path traversal via crafted filenames — store server-generated names only.
- Orphan files on crash — reconcile with DB rows in deletion/maintenance jobs.

## Implementation Notes

- Limits: max 10 photos per element, 5 MB each, JPEG/PNG/WebP only.
- Public photo URLs remain opaque ids; never expose filesystem paths to clients.
