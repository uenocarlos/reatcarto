# ADR-006: Evolve Procedural PHP as Authoritative Backend

## Status

Accepted

## Date

2026-07-31

## Context

The product already ships a React/Vite/Capacitor client and a procedural PHP surface under `php/` that talks to PostgreSQL/PostGIS. The client currently mocks persistence in localStorage and bypasses login. The PRD requires integrating with the existing PHP backend or a compatible successor while preserving recognizable Leaflet and field workflows.

## Decision

Evolve the existing procedural PHP API as the authoritative backend. Introduce shared configuration (`php/config.php` + environment variables), versioned SQL migrations, and new/rewritten endpoints for auth, maps, elements, photos, sync, publication, public gallery, administration, and account deletion. Keep the frontend `api.*` facade and replace localStorage implementations with `fetch` to `/php/...` using `credentials: 'include'`.

## Alternatives Considered

### Alternative 1: Replace PHP with Laravel or Node successor

- **Description**: Rewrite the API in a modern framework while keeping HTTP compatibility.
- **Pros**: Stronger structure, easier testing conventions, richer ecosystem.
- **Cons**: Large rewrite before auth, sync, and publication land; discards working PostGIS PDO patterns.
- **Why rejected**: Scope delivery depends on reconnecting the existing stack, not replacing it.

### Alternative 2: Split auth service from map/PostGIS PHP

- **Description**: Separate identity service; PHP retains only geospatial routes.
- **Pros**: Clear service boundaries.
- **Cons**: Dual session models, extra ops, and integration risk for a single-app product.
- **Why rejected**: Unnecessary complexity for the current deployment model.

## Consequences

### Positive

- Reuses existing PostGIS usage and session cookie direction.
- Frontend packages and map editor remain intact behind the API facade.
- Credentials move out of hardcoded PHP into env-backed config.

### Negative

- Procedural PHP requires discipline for shared helpers (auth guards, validation, JSON errors).
- No framework routers or ORM; contracts must be documented carefully.

### Risks

- Endpoint sprawl — mitigate with a thin shared bootstrap and consistent response envelope.
- Accidental localStorage authority remaining — remove mock paths once server wiring ships.

## Implementation Notes

- Add Vite proxy for `/php` in development.
- Guard every mutating and private-read endpoint with session checks and ownership/role authorization.
- Do not migrate existing localStorage map data into the account system.
