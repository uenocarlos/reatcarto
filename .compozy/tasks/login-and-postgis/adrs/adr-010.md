# ADR-010: IndexedDB Outbox with Optimistic Conflict Snapshots

## Status

Accepted

## Date

2026-07-31

## Context

Field work requires offline editing of prepared owned maps, visible pending state, safe retries, and explicit conflict resolution. The PRD forbids silent last-write-wins and forbids treating device storage as an independent authority. Existing localStorage mocks are not suitable as the long-term offline store.

## Decision

Implement account-bound offline persistence in IndexedDB: cached maps/elements/photos for prepared maps, plus an outbox of mutations with statuses `pending`, `synced`, `failed`, and `conflicted`. Each mutation carries a stable `client_mutation_id`. The server enforces optimistic concurrency via monotonic `version` on maps, elements, and photos. On version mismatch, the sync API returns both local-intended and remote snapshots; the UI requires an explicit user choice before writing the winning version. Logout attempts sync first and clears IndexedDB private data for the account only after success or explicit discard confirmation. Existing local-only localStorage maps are not imported.

## Alternatives Considered

### Alternative 1: Evolve localStorage as the offline store

- **Description**: Keep current keys with richer sync metadata.
- **Pros**: Minimal new client infrastructure.
- **Cons**: Quota and performance limits; poor binary photo handling; easy cross-account leakage if not carefully keyed.
- **Why rejected**: Insufficient for maps, photos, and durable outbox semantics.

### Alternative 2: Capacitor Filesystem JSON as primary sync store

- **Description**: Persist queues as files.
- **Pros**: Familiar on native.
- **Cons**: Weaker querying; awkward for web; tiles already use filesystem separately.
- **Why rejected**: IndexedDB fits structured outbox better; filesystem remains for offline tiles only.

### Alternative 3: CRDT automatic merge

- **Description**: Automatically merge concurrent geometry/metadata.
- **Pros**: Fewer user prompts.
- **Cons**: Can silently produce wrong field truth; conflicts with PRD explicit choice requirement.
- **Why rejected**: PRD mandates preserving both versions until the user chooses.

## Consequences

### Positive

- Idempotent retries via `client_mutation_id`.
- Conflicts are user-visible and auditable in the client.
- Account-bound keys enable safe multi-user devices after logout cleanup.

### Negative

- Conflict UI and snapshot storage add client complexity.
- Large maps need progressive cache and storage-quota messaging.

### Risks

- Dual-device offline divergence producing many conflicts — mitigate with clear per-item resolution and no silent replay of deletes into recreations.

## Implementation Notes

- Prepare-for-offline is an explicit user action that downloads authoritative server state into IndexedDB.
- Unprepared maps show unavailable offline rather than partial data.
- Server rejects recreating remotely deleted resources from stale local creates unless the conflict flow explicitly chooses recreation semantics documented as a deletion conflict.
