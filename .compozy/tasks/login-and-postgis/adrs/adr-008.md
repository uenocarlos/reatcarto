# ADR-008: Versioned Normalized PostgreSQL/PostGIS Schema

## Status

Accepted

## Date

2026-07-31

## Context

Current persistence is inconsistent: opportunistic `mapas` DDL, a `social` table with PostGIS geometry and JSON properties, mismatched `map_id`/`mapa_id` keys, and missing `ST_AsGeoJSON` on reads. Accounts, publication, audit, sync versions, and photos require a coherent authoritative model.

## Decision

Introduce versioned SQL migrations that create a normalized schema: `users`, `maps`, `map_elements` (PostGIS `geometry(Geometry,4326)`), `photos`, auth token tables, `audit_events`, and supporting uniqueness/consent fields. Map semantically from the legacy tables where useful, but do not treat the current `social` JSON layout as the long-term contract. All geometries use SRID 4326; invalid GeoJSON is rejected before insert. Resource rows that participate in sync carry a monotonic `version` integer and accept idempotent `client_mutation_id` values.

## Alternatives Considered

### Alternative 1: Minimal ALTER of `usuarios` / `mapas` / `social`

- **Description**: Patch existing tables only.
- **Pros**: Faster first write.
- **Cons**: Preserves broken contracts and JSON-as-schema ambiguity.
- **Why rejected**: Auth, audit, publication, and sync need first-class columns and constraints.

### Alternative 2: Document-style element storage only

- **Description**: Keep elements as JSON documents without typed geometry columns.
- **Pros**: Flexible fields.
- **Cons**: Weak spatial validation and indexing; fights PostGIS strengths.
- **Why rejected**: PRD requires durable PostGIS geospatial records.

## Consequences

### Positive

- Clear ownership FKs, GIST indexes, and cascade deletes.
- Sync and conflict handling have explicit version fields.
- Public gallery queries filter on publication/moderation columns without leaking private rows.

### Negative

- Requires a one-time cutover from any legacy table names/shapes.
- Migration tooling must be added to a previously migration-less repo.

### Risks

- Partial cutover leaving dual writes — ship a single migration path and retire legacy endpoints that write `social`.

## Implementation Notes

- Store migrations under `php/migrations/` (or `db/migrations/`) applied by a small PHP CLI.
- `public_id UUID` on maps is allocated at map creation and used for public routes when published.
- Soft-delete is not used for accounts after confirmed deletion; hard-delete product data and free username/email uniqueness.
