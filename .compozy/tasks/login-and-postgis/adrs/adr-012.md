# ADR-012: Vitest and PHPUnit Test Strategy

## Status

Accepted

## Date

2026-07-31

## Context

The repository has no test runner today. The feature spans React client behavior (auth gates, IndexedDB outbox, conflict UI) and PHP/PostGIS authorization and sync contracts. `_tests.md` requires an executable strategy.

## Decision

Adopt Vitest for frontend unit and component/integration tests (validation, outbox, auth context, API client mapping) with fakes at `fetch` and IndexedDB boundaries. Adopt PHPUnit (or equivalent PHP test harness) for API contract and domain tests against a disposable PostgreSQL/PostGIS database. Treat Playwright (or similar) end-to-end smoke as optional follow-on for critical journeys once the API and client are stable; primary journey coverage in v1 may use API-level integration plus focused UI tests where cheaper.

## Alternatives Considered

### Alternative 1: PHP API tests only

- **Description**: Skip frontend test runner.
- **Pros**: Less tooling.
- **Cons**: Offline outbox and conflict UX are client-heavy and would go unverified.
- **Why rejected**: ADR-010 logic lives primarily in the client.

### Alternative 2: Playwright as the primary suite from day one

- **Description**: E2E-first verification.
- **Pros**: High confidence on journeys.
- **Cons**: Slow, brittle, expensive while contracts are still moving.
- **Why rejected**: Unit/API contracts should stabilize first; E2E remains optional smoke.

## Consequences

### Positive

- Matches `_tests.md` layering.
- Enables CI gates on auth isolation and geometry validation early.

### Negative

- Requires introducing Composer/PHPUnit and Vitest into a previously untested repo.

### Risks

- Flaky DB tests — use transactional fixtures or recreated schema per suite.

## Implementation Notes

- Add npm scripts `test` / `test:unit` and PHP `composer test` (or `phpunit`) documented in the TechSpec sequencing.
- Never commit real SMTP or production DB credentials in fixtures.
