# ADR-003: Account-Bound Offline Editing and Explicit Conflict Resolution

## Status

Accepted

## Date

2026-07-31

## Context

Field workers frequently lose connectivity, and the existing product already supports local map behavior. Requiring continuous connectivity would undermine its field purpose, but silent conflict resolution could destroy collected work.

## Decision

Creating and editing maps requires a verified account, but an authenticated user may view and edit previously downloaded owned maps while offline. Local changes remain visibly pending and synchronize when connectivity returns. When the same item changed remotely and locally, preserve both versions and require the user to choose which result to keep. Before logout, attempt synchronization and then remove private cached data; when pending changes cannot synchronize, require explicit confirmation before discarding them. Do not import data from the current local-only version into the new account system.

## Alternatives Considered

### Alternative 1: Online-only editing

- **Description**: Block all map work when disconnected.
- **Pros**: Simplest consistency model.
- **Cons**: Fails the product's field-use context.
- **Why rejected**: The user explicitly selected offline viewing, editing, and later synchronization.

### Alternative 2: Last write wins

- **Description**: Keep whichever change has the latest timestamp.
- **Pros**: No user intervention.
- **Cons**: Can silently discard valid field work and depends on trustworthy device clocks.
- **Why rejected**: The user selected manual conflict resolution.

## Consequences

### Positive

- Field collection remains usable without connectivity.
- Conflicting work is not silently overwritten.
- Logout does not casually expose another user's cached private maps.

### Negative

- Users may need to resolve conflicts before work is fully synchronized.
- There is no migration path for maps stored by the existing local-only version.

### Risks

- Interrupted synchronization can duplicate or partially apply operations; retries must be safe and progress must remain visible.
- Logout with pending changes creates a loss decision; the warning must identify what has not synchronized.

## Implementation Notes

The TechSpec must define the offline operation model, conflict identity and comparison rules, idempotent synchronization, local data protection, retry behavior, and deletion propagation.
