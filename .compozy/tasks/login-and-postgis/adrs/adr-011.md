# ADR-011: Admin Bootstrap Seed and Identity Reuse After Deletion

## Status

Accepted

## Date

2026-07-31

## Context

The product has exactly two roles: field user and administrator. Field users must not self-elevate. The PRD leaves first-administrator creation and post-deletion identity reuse to the TechSpec. Permanent deletion must not restore prior maps when the same email or username returns.

## Decision

Bootstrap the first administrator through a deploy-time PHP CLI/seed that reads `ADMIN_EMAIL`, `ADMIN_USERNAME`, and `ADMIN_PASSWORD` from the environment, creates a verified active admin only when no administrator exists, and otherwise exits without promoting anyone. No HTTP endpoint grants the admin role. After confirmed permanent account deletion, remove product data (profile, sessions, maps, elements, photos, publication, tokens) and free email and username for new registration. A new account with a recycled identity starts empty and never inherits prior ownership or maps. Locked-admin recovery uses password reset for that admin email plus server/env access to re-seed only when zero admins remain (or operational password reset at the database/mail layer)—never an in-app promote path.

## Alternatives Considered

### Alternative 1: First registered user becomes admin

- **Description**: Automatic elevation of account #1.
- **Pros**: Zero ops tooling.
- **Cons**: Dangerous on public registration; races; accidental admin.
- **Why rejected**: Open registration makes this unsafe.

### Alternative 2: Permanent tombstones for email/username

- **Description**: Never reuse identifiers after deletion.
- **Pros**: Stronger forensic linkage.
- **Cons**: Blocks legitimate re-enrollment and support scenarios.
- **Why rejected**: PRD allows reuse without restoring state; free identifiers after erase are sufficient.

### Alternative 3: Manual SQL-only admin creation with no CLI

- **Description**: Document raw inserts for operators.
- **Pros**: No seed code.
- **Cons**: Easy to mishandle password hashes and verification flags.
- **Why rejected**: Seed CLI encodes the correct invariants.

## Consequences

### Positive

- Clear operational path for first admin.
- Deletion meets privacy expectations without identity permanent lockout.
- Role model stays closed.

### Negative

- Operators must manage env secrets for bootstrap.
- Recycled identifiers can confuse humans reading old audit rows that reference deleted user ids.

### Risks

- Seed rerun with different credentials after an admin exists — seed must no-op when any admin exists.
- Audit rows referencing deleted users — retain immutable audit with opaque user ids even after account erase where legally retained; product UI simply has no live account.

## Implementation Notes

- Roles stored as constrained enum/check: `field` | `admin` (map from legacy `role_id` during migration).
- Deactivation is distinct from deletion; deactivated accounts keep identifiers reserved.
