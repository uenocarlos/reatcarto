# ADR-007: Cookie-Based PHP Sessions and Multi-Device Policy

## Status

Accepted

## Date

2026-07-31

## Context

Authentication must protect every server operation. The legacy `login.php` already establishes `$_SESSION['usuario_id']` with CORS credentials. The PRD forbids social login and SSO, requires dual-identifier login, email verification, recovery, and safe logout.

## Decision

Use native PHP sessions delivered via secure cookies (`HttpOnly`, `Secure` in production, `SameSite=Lax` or `Strict` as appropriate for Capacitor/web). Expose `register`, `verify`, `login`, `logout`, `me`, recovery, and profile endpoints on the same session model. Allow multiple concurrent sessions per account. Invalidate only the current session on logout. Globally invalidate all sessions for an account on password change, password reset completion, administrator deactivation, and account deletion. Store session metadata needed for global invalidation (for example session id registry keyed by user) when file sessions alone cannot revoke siblings reliably.

## Alternatives Considered

### Alternative 1: Opaque bearer tokens in Authorization header

- **Description**: Issue server-side tokens; client stores and sends them.
- **Pros**: Explicit API style; easier cross-origin without cookies.
- **Cons**: XSS storage risk if placed in localStorage; duplicates what PHP sessions already provide.
- **Why rejected**: Cookie sessions already match Capacitor/web credentialed fetch and existing PHP.

### Alternative 2: Stateless JWT without server session

- **Description**: Signed JWT as sole auth proof.
- **Pros**: No server session store.
- **Cons**: Harder immediate revocation on deactivation/password reset without a denylist that reintroduces state.
- **Why rejected**: Privileged account lifecycle needs prompt revocation.

## Consequences

### Positive

- Immediate server-side revocation path for security events.
- Aligns with existing PHP login pattern.
- Multi-device field use remains possible.

### Negative

- Requires careful CORS, cookie, and Capacitor WebView configuration.
- Global invalidation needs a session registry or equivalent.

### Risks

- Misconfigured SameSite breaking mobile WebView login — verify on Android Capacitor early.
- Session fixation — regenerate session id on privilege changes (login, password reset).

## Implementation Notes

- Login accepts username or email; responses never disclose which identifier matched on failure.
- Pending-verification and deactivated accounts receive distinct, non-enumerating messaging only after successful credential check where the PRD requires status explanation.
- `ProtectedRoute` and `App.jsx` must stop bypassing authentication.
