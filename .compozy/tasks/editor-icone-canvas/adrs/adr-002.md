# ADR-002: Per-User Icon Library Without Editable Scene Replay

## Status

Accepted

## Date

2026-08-12

## Context

Applying a drawing only as a one-off `custom_icon_url` on a single point forces users to redraw the same symbol for every marker. Stakeholders want reuse across points and maps. They also rejected vector scene re-edit: opening the editor always starts a blank canvas for a new drawing. Persistence must therefore treat the exported PNG (plus metadata such as optional name) as the reusable asset, not an in-editor object graph.

## Decision

1. Each confirmed drawing is saved into a **per-user icon library** available on all maps owned/edited under that account.
2. Confirming in the editor **saves to the library and applies** the icon to the point currently being styled (`custom_icon_url` or equivalent already used by the product).
3. Opening the drawing editor always presents a **clean canvas** for a new icon; there is no “resume objects” edit of a past drawing.
4. Library MVP actions: pick/apply to current point, remove from library, optional name at save time.
5. Removing an icon from the library does **not** clear `custom_icon_url` on points that already use it; those points keep showing the applied asset until the user changes the point’s icon.
6. Entry point for library and editor in MVP: **StylePanel** while creating/editing a point only (section “Meus ícones” + open editor). No separate library management page.

## Alternatives Considered

### Alternative 1: One-shot PNG on the point only

- **Description**: Apply PNG to `custom_icon_url`; no library.
- **Pros**: Smallest scope; matches today’s field.
- **Cons**: No reuse across points/maps; user must redraw.
- **Why rejected**: Explicit user requirement for a reusable icon base.

### Alternative 2: Persist editable scene and reopen for edit

- **Description**: Store object graph; reopen editor with prior objects.
- **Pros**: True re-edit of drawings.
- **Cons**: Extra persistence model; canvas never “new drawing”; higher MVP cost.
- **Why rejected**: User chose clean-canvas new drawings and library reuse of baked icons.

### Alternative 3: Per-map or org-shared library

- **Description**: Scope icons to a map or organization.
- **Pros**: Collaboration / map-packaged assets.
- **Cons**: Blocks cross-map personal reuse; org sharing needs permissions model.
- **Why rejected**: User chose account-scoped personal library for MVP.

## Consequences

### Positive

- Users build a personal symbol set once and reuse it.
- Editor stays simple (always new drawing).
- Aligns with cartographic workflows (symbol library + apply to features).

### Negative

- New product entity (user icon library) beyond a single style field.
- Orphaned point references after library delete must remain valid visually.
- No in-place fix of a bad drawing — user draws a new icon and re-applies.

### Risks

- Library growth without quotas — mitigate later if needed; MVP has no hard count limit (size per icon is capped — see ADR-004).
- Points referencing removed library entries need durable asset URLs — TechSpec must not delete underlying media while points still reference it, or must keep serving bytes for applied URLs.

## Implementation Notes

Product rule: library membership and point application are separate. Delete-from-library is catalog hygiene, not cascade-delete on map elements. Storage/upload alignment with existing media patterns is a TechSpec concern; the PRD requires durable, reusable URLs suitable for `custom_icon_url`.
