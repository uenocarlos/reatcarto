# ADR-006: user_icons Table and /php/icons API with Soft Library Remove

## Status

Accepted

## Date

2026-08-12

## Context

Photos are element-scoped (`element_id`, cascade with element) and must not become the user-facing icon catalog. The PRD requires an account-scoped library, durable URLs in `style.custom_icon_url`, and remove-from-library without clearing points that already use the asset.

## Decision

1. Add Postgres table `user_icons` owned by `user_id`, storing PNG metadata + `storage_key` under `uploads/` (same root pattern as photos).
2. Expose PHP endpoints under `/php/icons/` (list, upload/create, get, soft-remove) and `/php/public/icon.php` for public references.
3. **Soft-remove:** set `library_hidden_at` (timestamptz). List endpoints omit hidden rows. Rows and files remain; `GET` continues to serve bytes for authorized/public references.
4. Persist on points: `style.custom_icon_url = "/php/icons/get.php?id=<uuid>"` (authenticated shape). Public element payloads may rewrite to `/php/public/icon.php?id=<uuid>` when serializing public views.
5. Limits: `MAX_ICON_BYTES = 200 * 1024`, canvas 256×256 enforced client-side before upload; server rejects non-PNG and oversize. `MAX_ICON_NAME_LENGTH = 100`; blank/whitespace → fallback name `"Ícone"`.
6. Library mutations (create/list/remove) require online `require_active_user`; no offline outbox for icons in MVP.

## Alternatives Considered

### Alternative 1: Hard-delete file on remove

- **Pros**: Reclaims disk.
- **Cons**: Breaks existing point markers.
- **Why rejected**: Violates ADR-002 / PRD non-cascade rule.

### Alternative 2: Data URLs in style / client-only library

- **Pros**: No new API.
- **Cons**: JSONB bloat; no cross-device library; weak ACL.
- **Why rejected**: User chose server library entity.

### Alternative 3: Reuse `photos` table

- **Pros**: Less new code.
- **Cons**: Wrong ownership model; mixes attachments with symbols.
- **Why rejected**: Explicit PRD constraint.

## Consequences

### Positive

- Clear product entity for “Meus ícones”.
- Points keep working after catalog remove.
- Mirrors proven upload/serve patterns from photos.

### Negative

- Orphan/hidden files need eventual GC policy (out of MVP).
- New migration and PHP surface area.

### Risks

- Disk growth from hidden icons — mitigate later with GC when no element references the URL.

## Implementation Notes

Follow `PhotoService` structure in `php/lib/Icons/IconService.php`. Add constants to `Limits.php`. Support optional `client_mutation_id` on create for idempotent double-submit (same as photos).
