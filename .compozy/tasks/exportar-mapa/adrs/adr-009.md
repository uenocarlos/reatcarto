# ADR-009: Static Brazilian Admin Boundaries under public/geo

## Status

Accepted

## Date

2026-08-03

## Context

Location insets require UF and municipality geometries (printJs municipal pipeline). Current PHP API has no `dataservice/get_municipios.php` equivalent. Insets are owner-facing only, not a public geo download product.

## Decision

Ship **static GeoJSON (EPSG:4326)** assets under **`public/geo/`**, loaded by the export client only when insets (or municipal mesh) are enabled:

| Asset | Role |
|-------|------|
| `public/geo/states.geojson` | Brazilian states for inset/context styling |
| `public/geo/municipalities.geojson` | Municipal mesh / selection geometries |

Load via `fetch('/geo/...')` with in-memory session cache after first successful fetch. Selection lists (UF codes/names, municipalities per UF) derived from feature properties. On fetch/parse failure, surface explicit error state; never claim a complete political basemap (US-008.EC-1).

No authenticated geo endpoint required for v1. Main map export remains possible if the owner sets location maps to **none** even when geo assets fail.

## Alternatives Considered

### Alternative 1: Authenticated PHP endpoint

- **Description**: Serve clipped GeoJSON from disk via `php/geo/*.php` with session.
- **Pros**: Optional ownership gating; smaller public footprint.
- **Cons**: Extra API surface for data that is public administrative boundaries; unnecessary for owner-only UI.
- **Why rejected**: Design chose static hosting.

### Alternative 2: Live CDN / IBGE network fetch

- **Description**: Client hits external endpoints per session.
- **Pros**: No repo bulk.
- **Cons**: Offline fragility, CORS, rate limits, unstable product SLA.
- **Why rejected**: Prefer product-owned static assets.

### Alternative 3: Per-UF municipality files (hybrid)

- **Description**: Bundle UF global + load `/geo/municipalities/{uf}.geojson` on demand.
- **Pros**: Smaller initial load.
- **Cons**: More files/ops complexity; deferred unless payload forces it.
- **Why rejected**: User chose single static tree under `public/geo/` (A).

## Consequences

### Positive

- Zero new PHP surface for geo; cacheable by CDN/static hosting.
- Clear failure semantics for missing files.

### Negative

- Large municipal GeoJSON increases repo and deploy size; may need polygon simplify offline before commit.

### Risks

- Bundle size too large for first paint of whole SPA → acceptable because files load only when insets enabled; if still huge, implementers may split per-UF files without changing ADR intent (same `public/geo/` root).

## Implementation Notes

Document source (e.g. IBGE simplified) and property schema (`SIGLA_UF`, `CD_MUN`, `NM_MUN` or project-normalized aliases) in code comments next to the loader. CRS always 4326 to match PostGIS geometries and Leaflet.
