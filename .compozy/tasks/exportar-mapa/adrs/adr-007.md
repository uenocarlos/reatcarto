# ADR-007: Server-Backed export_settings with IndexedDB Mirror

## Status

Accepted

## Date

2026-08-02

## Context

Export composition must restore per map (ADR-004). The `maps` table has no settings column today. Account sync already mirrors owned maps into IndexedDB. Multi-device edits and offline field use require a clear conflict rule that does not reopen the geometry conflict UI.

## Decision

- Add `maps.export_settings JSONB NOT NULL DEFAULT '{}'::jsonb`.
- Include `export_settings` in `format_map_record` and in map get/list/update responses.
- Persist from the client with debounce (~500ms) on option changes plus flush on modal close and before/after successful export attempt.
- Mirror the field in the existing IndexedDB map cache so offline reopen restores the last known settings.
- **Last-write-wins** on `export_settings` only. Updates that change solely `export_settings` do not require `base_version`, do not increment `maps.version`, and never surface the geometry conflict modal.
- Corrupted or schema-invalid JSON falls back to documented defaults without crashing.
- Stale element visibility ids are ignored on restore.

## Alternatives Considered

### Alternative 1: Device-only IndexedDB

- **Description**: No server column.
- **Pros**: No migration.
- **Cons**: No cross-device restore.
- **Why rejected**: User chose server + IndexedDB.

### Alternative 2: Versioned conflict UI for settings

- **Description**: Treat settings like geometry updates.
- **Pros**: Symmetric concurrency model.
- **Cons**: Forces field users through conflict UI for legend tweaks.
- **Why rejected**: User chose LWW outside geometry conflicts.

### Alternative 3: Dedicated PATCH without map payload

- **Description**: Separate `/maps/:id/export-settings` route only.
- **Pros**: Clear separation.
- **Cons**: Extra endpoint surface; same ownership checks.
- **Why rejected**: Prefer extending `maps/update` with a settings-only fast path unless implementation later splits for clarity; behavior remains LWW without version bump.

## Consequences

### Positive

- Settings follow the owner across devices when online.
- Geometry conflict flow stays focused on map data.

### Negative

- Two devices editing export options silently overwrite each other.

### Risks

- Large visibility maps in JSONB — mitigate by storing only hidden ids / sparse maps and pruning deleted elements on load.

## Implementation Notes

Migration under `php/migrations/`. Client: `src/lib/export/exportSettings.js` (normalize, defaults, validate, prune). Debounced save via existing `api.entities.Map.update` (or equivalent) with `{ id, export_settings }` only.
