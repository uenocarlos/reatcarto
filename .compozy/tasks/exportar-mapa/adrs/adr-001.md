# ADR-001: Full Feature Parity with Legacy printJs Export Window

## Status

Accepted

## Date

2026-08-03

## Context

ReatCarto already has a working map editor (Leaflet) but no export path in the React app. The legacy reference `.idea/printJs.php` is a complete cartographic export workstation: controllable layout, WYSIWYG preview, legend formatting, location insets, page and quality settings, and browser-side PNG/PDF download. Users need that same efficiency for reports and institutional maps; a reduced “screenshot only” export would break the existing cartographic workflow.

## Decision

Ship a map export experience with **full functional parity** with the printJs export window, adapted to this product’s authenticated map editor, styles, and UI system.

Parity includes, at minimum:

- Title, authorship, and technical-responsible text fields
- PNG and PDF output formats
- Paper sizes A4, A3, and Letter; landscape and portrait orientation
- DPI range 72–600 (default 300)
- Legend position: inside map, right of map, below map (with drag/resize where printJs supports it)
- Legend columns (1–6), font size (8–18 px), spacing (very compact → very loose)
- Layer visibility controls that build the legend from map content
- Optional map labels (“show names on map”)
- Basemap choice: OpenStreetMap, Carto-style light, satellite
- Location inset maps: none, one, or two; state and municipality selection; municipal mesh overlay; regional colors and optional state legend entries
- Map chrome: graphic scale, north arrow, graticule, decorative frame
- Fixed REAT/FURG institutional footer and logo (see ADR-004)
- Live or on-demand WYSIWYG preview and client-side export with loading feedback
- Usable on phone and desktop (see ADR-005)

Behavior must match printJs intent: configure → preview what will export → generate file at the chosen quality.

## Alternatives Considered

### Alternative 1: Minimal screenshot export

- **Description**: Capture the current map viewport only, with optional title.
- **Pros**: Faster to ship; fewer dependencies on geographic data.
- **Cons**: Loses professional layout, legend, insets, paper, and DPI control.
- **Why rejected**: User required the same functionality as printJs.

### Alternative 2: Layout subset without location insets

- **Description**: Keep paper/legend/quality but drop Brazil state/municipality insets.
- **Pros**: Avoids municipal GeoJSON and dual inset maps.
- **Cons**: Major loss for Brazilian institutional cartography in the legacy tool.
- **Why rejected**: User explicitly chose full parity including location maps.

## Consequences

### Positive

- Owners regain the full cartographic export capability from the legacy app inside the modern product.
- Downstream tasks have a crisp functional baseline: printJs capability catalog.

### Negative

- Larger product surface: location data, dual inset maps, legend layout, high-DPI capture.
- High-DPI exports remain demanding on device memory and time.

### Risks

- Location mesh/services missing in the current repo → product must deliver equivalent geographic data access; techspec defines sources and caching (see Open Questions in PRD).
- Client-side capture may fail or produce incomplete basemap tiles → transparent error messaging and wait-for-tiles behavior.

## Implementation Notes

Product definition only. Stack, capture libraries, and IBGE or other data services belong to the TechSpec. Efficiency requirement: export remains browser-local download after client composition (same class of approach as printJs, not a remote print farm), unless a later ADR supersedes this.
